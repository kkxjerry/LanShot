## 当前剩余薄弱题

### 01 Function Calling / ReAct：81

主要漏：

- 工具选择正确率
- 参数结构正确率
- 参数内容正确率
- 端到端任务完成率

需要把“格式合法 != 选对工具 != 参数正确 != 业务完成”压成一条短口径。

### 02 超长 JSON：78

主要漏：

- 优先缩小一次生成规模
- Syntax / Schema / Business 三层校验

现有答案偏在“怎么补截断”，少了“先别生成这么大”。

### 04 Agent评测：79

主要漏：

- 多条合法轨迹不能严格逐跳匹配
- 代码断言 + LLM Judge + 人工校准
- 副作用控制

这题更像通用知识卡不够完整，不是项目RAG问题。

### 07 CODA工程难点：79

答案过度聚焦多文件事务，漏了宏观 Plan 主线：

Planner → DAG → 依赖/环校验 → Runtime 调度。

需要让“工程难点”问题至少覆盖宏观架构 + 一个最深工程坑。

### 08 多工具并发：83

缺一个非常关键的边界：

同一轮模型已经同时生成 read 和 write 参数，即使 Runtime 把它们排成先读后写，write 参数也不会自动利用 read 的新结果；有数据依赖时必须拆到下一轮模型调用。

### 11 并发上传：84

主要漏：

- 锁过期后的旧 Worker 需要 fencing/version 防残留写
- 内容寻址 CAS != Compare-and-Swap

### 12 高压排期：68

现在最弱。

缺：

- 必须交付项与验收条件先对齐
- 范围变化及时向负责人确认
- 遗留代码先找入口 / 数据影响 / 回归范围
- 上线前2小时发现 P0：无法安全隔离和充分验证时应建议暂停/延期，而不是泛泛“先降级”
- 测试分层需要更具体

这一题不是 RAG 技术知识问题，更像业务/工程表达模板问题。
